# アプリケーションセキュリティチェック

このスキルは、`python-ai-application`（Streamlit + Gemini APIの個人用ライティングツール）に対して、
コードを実際に読み・検索した上で、次の2つの観点だけに絞ってセキュリティチェックを行う。

このアプリはデータベースも認証もない個人・単一ユーザー向けのローカルツールであることを前提にする。
そのため「他人に攻撃される」リスクよりも、「自分のAPIキーや情報が意図せず漏れる／記録される」リスクと、
「貼り付けたテキストによってAIの挙動が意図せず乗っ取られる」リスクを中心に見ること。過剰に大げさな
指摘（例: 個人用ツールにログイン機能がない、CSRF対策がない等）はしない。的外れな一般論より、
このコードベースの実際の書き方に即した具体的な指摘を優先する。

## 観点1: APIキー・機密情報の扱い

以下を実際にファイルを開いて確認する。

- **`.gitignore` の内容**（`.gitignore` を読む）: `.env` が除外対象に含まれているか。
- **リポジトリ内にAPIキーが直書きされていないか**: `utils/gemini_client.py`、`check_setup.py`、
  `pages/*.py`、`app.py` などを対象に、`api_key=` や `GEMINI_API_KEY` 周辺のコードを読み、
  文字列リテラルのキーがハードコードされていないかを確認する（`Grep` で `AIza` や
  `api_key\s*=\s*["']` のようなパターンを探すとよい）。
- **APIキーの取得経路**: `utils/gemini_client.py` の `get_api_key()` が
  `st.session_state` → 環境変数 `GEMINI_API_KEY` の順で読んでいるか、キーをファイルやログに
  書き出していないかを確認する。
- **エラーメッセージでの漏洩**: `generate()` の `except Exception as exc` で例外メッセージを
  そのまま `f"...{exc}"` のように画面に出している箇所（`RuntimeError` → `st.error()`）で、
  APIキーの値そのものが例外メッセージに含まれて表示される可能性がないかを確認する。
  （Gemini SDKの例外にAPIキー文字列が含まれるケースがないか、実際に読んで判断する）
- **`.env` 関連ファイルの状態**: `.env.example` はコミット対象でよいが、実際の `.env`
  （キーの値が入ったファイル）がリポジトリ内に存在し追跡されていないかを確認する
  （`git status` や `git ls-files` が使えるならそれで確認し、Gitリポジトリでない場合は
  ファイルの有無だけ確認する）。
- **サイドバー入力のAPIキーの扱い**: `utils/ui.py` の `setup_sidebar()` で、入力されたAPIキーが
  `st.session_state` 以外（ファイル、`st.write` によるデバッグ出力、他のウィジェットの
  `value=` など）に漏れて表示・保存されていないかを確認する。

## 観点2: プロンプトインジェクション対策

各ページ（`pages/*.py`）は、ユーザーが入力した自由記述のテキスト（メール本文、要約対象の文章など）を、
そのまま文字列としてGeminiへのプロンプトに埋め込んでいる。これは「他人からの攻撃」ではなく、
「ユーザーがどこかからコピペした文章（他人からのメール本文や記事など）に、AIへの指示のように読める
文言が紛れ込んでいた場合、意図しない出力になる」というリスクとして評価すること。

以下を確認する。

- 各ページのプロンプト組み立て部分（`prompt = f"""..."""` の箇所）で、ユーザー入力が
  `# 元の文章` や `# 受信したメール本文` のような見出しの下に明確に区切られて埋め込まれているか
  （区切りが曖昧だと、AIがどこまでが「指示」でどこからが「データ」か混同しやすくなる）。
- プロンプトの冒頭で役割（例:「あなたはプロのブログライターです」）が明示されており、
  ユーザー入力側の文章で役割や出力形式を上書きされにくい構成になっているか。
- 生成された結果（`generate()` の戻り値）が、`show_result()` で表示・ダウンロードされる以外の
  用途（例: シェルコマンドの実行、他のAPI呼び出し、ファイルパスとしての利用）に使われていないか。
  もし生成結果を何かの「実行」に使っている箇所があれば、それは深刻な指摘として扱う。
- プロンプトインジェクション自体を完全に防ぐことは（システムプロンプトの工夫だけでは）原理的に
  難しいため、「完全に防げていない」こと自体は指摘の対象にしない。指摘すべきなのは、
  「入力とAI出力の扱われ方によって、実害（情報漏洩・意図しない実行・APIキー漏洩など）に
  つながるかどうか」である。

## チェックの進め方

1. 対象ファイルを実際に `Read` する（推測で書かない）。関連しそうな箇所は `Grep` で横断的に検索する。
2. 上記2つの観点それぞれについて、見つかった内容を評価する。問題がなければ「問題なし」の
   項目として明示する（黙って省略しない）。
3. 下記のフォーマットでチャットに直接レポートを出力する。ファイルの作成・保存はしない。

## 出力フォーマット

必ず次の構成でレポートする。

```
## セキュリティチェック結果（観点: APIキー・機密情報 / プロンプトインジェクション）

重大な問題: N件 / 改善余地あり: N件 / 問題なし: N件

### 🔴 重大（すぐ対応すべき）
- [対象ファイル:行] 内容の説明
  → 推奨対応

### 🟡 改善余地あり
- [対象ファイル:行] 内容の説明
  → 推奨対応

### 🟢 問題なし
- 確認した項目を簡潔に列挙
```

該当する指摘がないカテゴリ（🔴や🟡）は見出しごと省略してよいが、🟢（確認したが問題なかった項目）は
必ず記載し、「何を確認して問題なかったのか」が分かるようにする。指摘は具体的なファイル名・行番号・
関数名で示し、なぜ問題なのか、どう直すとよいかを一言添える。
